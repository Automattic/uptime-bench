Jetmon v2 vs. the uptime monitoring field

Over a series of controlled uptime-bench runs, Jetmon v2 moved from a promising in-house monitor with several blind spots to the strongest all-around detector in the latest feature matrix. The biggest story is not that it became the fastest service. It did not. The bigger story is that it became broad, consistent, and much better at classifying what actually failed.

Short Version

The latest all-service feature matrix ran 33 scenario samples per service across HTTP, TCP, content, DNS, TLS hard failures, TLS advisories, method-specific failures, custom headers, partial responses, and response-time thresholds. Jetmon v2 passed every comparable sample: 32 passed, 0 failed, and 1 excluded because response-time-threshold checks are not currently supported by the Jetmon v2 adapter.

Jetmon v1 did not perform competitively in the same test harness. In the latest matrix it passed 0 of 25 comparable samples and had 8 capability mismatches. Earlier v1-inclusive runs showed the same pattern: the current v1 adapter/bridge path can be included in the tests, but it is not reliably detecting the scenario set.

Methodology and Caveats

These results come from uptime-bench, a harness that provisions monitors, injects a controlled failure into target infrastructure, waits for the failure window and grace period, retrieves provider events, and scores the result against ground truth.

These are not vendor marketing numbers and they are not universal product guarantees. They are verified behavior for the services as configured in this harness, using the adapters available at the time of each run. Some rows have only one or two samples in the latest feature matrix, so treat those cells as confirmed smoke-level evidence rather than final statistical proof.
  • Probe geography differs. SaaS services and self-hosted services do not have identical vantage points.
  • Some services support a feature natively; others cannot configure it and are marked as unsupported.
  • Unsupported and inconclusive results are not counted as behavioral misses.
  • Detection latency is measured from injected failure start to first alert observed through the adapter API.

How Jetmon v2 Improved

The important caveat: these runs are not a perfectly stable benchmark suite. The test mix changed as the project learned where the weak spots were. A lower pass rate on a later date often means the run was intentionally focused on harder scenarios, not that the service got worse. With that caveat, the trend is still clear: Jetmon v2 repeatedly closed the gaps that the previous runs exposed.

Most meaningful fixes

The biggest improvements were not cosmetic. Jetmon v2 went from missing most partial response cases to passing them, from treating deprecated TLS as downtime to classifying it as an advisory, and from missing DNS failures to passing NXDOMAIN, SERVFAIL, DNS timeout, and CNAME-to-NXDOMAIN samples.

Remaining feature gap

Response-time-threshold monitoring is still not verified for Jetmon v2. In the latest run it was correctly excluded as unsupported rather than counted as a miss.

Detection Times

Jetmon v2 was not the fastest detector in the latest matrix. Its detection times clustered around the configured three-minute check cadence. That made it slower than Better Uptime, Gatus, and UptimeRobot on several cases, but faster and more predictable than Datadog Synthetics in this setup.

Classification Quality

A monitor that says "down" is useful. A monitor that says "DNS SERVFAIL," "TLS certificate expiring," or "truncated response" is more useful. This is where Jetmon v2's recent work became especially visible.

  • Deprecated TLS was correctly treated as an advisory by Jetmon v2, not a hard outage.
  • TLS expiring was detected as an advisory rather than downtime.
  • Hard TLS failures still stayed on the outage path.
  • DNS failures now produce distinct behavior for NXDOMAIN, SERVFAIL, timeout, and CNAME-to-NXDOMAIN cases.
  • Every successful Jetmon v2 outage sample in the latest matrix also produced recovery/closure data.

What I Would Compare Next

The current findings are strong enough for a first public write-up, but there are several comparisons that would make the story stronger over time.

  • Repeat the feature matrix with more samples per cell. The latest run is excellent for breadth, but some rows only have one or two samples.
  • Separate outage latency from advisory latency. Advisory workflows are different from paging workflows and should be measured separately.
  • Measure recovery latency. Alert fire time is only half the operational story.
  • Track provider/API reliability. Adapter errors, rate limits, and deprovision retries matter because they affect benchmark trust and real operational use.
  • Compare cost and check frequency. A service that checks every 30 seconds and one that checks every 3 minutes are not trying to be the same product.
  • Keep capacity testing separate. Jetmon v2 capacity work is a different benchmark lane and should not be mixed with feature detection claims unless the run was designed for both.

Takeaway

Jetmon v1, as currently exercised by the harness, does not stack up against the field. Jetmon v2 does. The latest feature matrix shows Jetmon v2 matching or beating the field on detection breadth, while also improving on the quality of the classification. Its biggest missing feature from this run is response-time-threshold support, and its biggest competitive tradeoff is detection speed: stable, roughly three-minute detection in this configuration, but not the fastest in the group.

The more interesting result is the improvement curve. The benchmark repeatedly found real defects, Jetmon v2 changed, and the next run verified whether those changes worked. That feedback loop is the part worth keeping.
